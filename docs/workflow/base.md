# 기본 작업 순서

## 공통 규칙

### 환경

커밋 메시지 룰은 로컬 llm을 사용하기 때문에 `git commit`명령어만 입력한다.

### 이름 규칙

이름 규칙을 사용하는 곳은 `{이름 규칙}`형식으로 작성됨 ex: `{이슈 기반 네이밍}`

- 이슈 기반 네이밍: `<이슈번호>-<기능-slug>` 기능 슬러그는 최대 10자 이내로 사용

## 브래인 스토밍

어떤 기능을 어떻게 만들건지 생각하고 평가해서 문서로 정리하는 단계
클로드 코드 `/superpowers:brainstorming` 사용
`docs/planning/features/{이슈 기반 네이밍}/` 디렉토리에 문서 작성
`readme.md` 내용 근거로 `github-issue` 스킬 사용해 git issue 생성

### 작성 문서

문서 작성 순서: readme.md → api-spec.md / page-spec.md → plan.md

#### readme.md

템플릿: [template/readme.md](./template/readme.md)

#### api-spec.md

템플릿: [template/api-spec.md](./template/api-spec.md)

#### page-spec.md

템플릿: [template/page-spec.md](./template/page-spec.md)

#### plan.md

- plan은 diff_code가 200줄 미만으로 생성되게 작업해야함
- 중간에 변경될수 있기 떄문에 세부적으로 작성하지 말고 토큰을 절약하면서 방향성만 맞도록 작성

템플릿: [template/plan.md](./template/plan.md)

### 완료 기준

- 어떤 기능을 만들어 어떤 문제를 해결할 것인지 정의 되었는가?
- 유저 플로우를 보고 사용자에 니즈를 해결하는가?
- 데이터가 필요하면 어떤 API를 만들것인가? 테스트 케이스는?
- 화면이 필요하면 어떤 페이지를 만들것인가? 테스트 케이스는?
- git issue 생성 되었는가?
- plan.md 각 작업 단위가 diff 200줄 미만으로 쪼개졌는가?

### 완료 후 작업

- 생성한 문서를 링크 리스트화해서 보여주고 작업을 요약해줘
- 생성한 이슈 링크 안내
- 다음 단계는 아래 단계로 넘어간다.

## 진행 방식 결정

`plan.md`의 내용을 기반으로 어떤 작업을 진행할지 사용자와 대화하여 결정한다.
서브 이슈 분리 필요성을 정한다. PR diff가 200줄이 넘긴다면 필요하다.
작업 시작전 브랜치 분리 작업을 진행한다.

### 서브 이슈 분리

작업이 많은 경우 서브 이슈로 나눠서 진행
작업할 내용을 정해서 이슈 생성하고 메인 이슈에 서브 이슈로 연결

이슈 내용은 아래 내용을 기반으로 작성한다.

```markdown
# 개요

간략하게 무슨 이슈인지 설명

# 목적

어떤 목적으로 이슈를 만들었는지 작성

# 구현 내용

어떻게 구현했는지 중요 내용을 기반으로 간략하게 작성

# 검증 방법

어떻게 검증하였는지 작성

# 완료 기준

- [ ] 체크리스트 방식으로 직접 확인 

# 참고 사항
없는 경우 제외

```

### 브랜치 분리

`features/{이슈 기반 네이밍}` 형식으로 브랜치 생성

## 작업 진행

`plan.md`와 `## 진행 방식 결정`에서 정해진 작업을 진행하며 아래 플로우를 따른다.

### 플로우

- **서브 이슈로 분리된 작업**(`## 진행 방식 결정` > `서브 이슈 분리`에서 나눈 경우)만 서브 플랜 문서를 쓴다. 해당 서브 이슈의 작업 내용을 기록하는 용도로, 어떤 작업을 할지 문서 및 이전 대화 내용을 검토하여 `docs/planning/features/{이슈 기반 네이밍}/subplan/` 아래 `plan-간단한 기능 제목.md`으로 작성한다.
  - 형식은 [template/subplan.md](./template/subplan.md) 고정(Goal/Spec/Files/Step 1~5). 배경·대안 비교 같은 서술은 기본 생략 — Files/Step만으론 설명이 안 되는 복잡한 Task일 때만 2~3줄 예외로 추가한다. (`/superpowers:writing-plans`는 구조 참고용으로만 사용)
  - Step 1/3엔 전체 코드를 쓰지 않는다. "개요"로 무엇을 검증/구현하는지만 적고, 실제 코드는 구현 단계에서 파일에 바로 작성한다.
  - 요청자에게 진행 여부를 확인 받는다.
  - 요청자 검토 후 수정 사항을 문서에 최신 반영하고 진행 여부를 재확인 받는다.
- **서브 이슈로 분리되지 않은 작업**은 서브 플랜 문서 없이 `plan.md`의 해당 Task를 바로 기준 삼아 진행한다.
- 서브 플랜(분리된 경우) 또는 `plan.md`의 Task(분리 안 된 경우)를 기반으로 작업을 진행한다.
aks   - Step 1(실패하는 테스트 작성) → Step 2(실패 확인) → Step 3(최소 구현) → Step 4(통과 확인) → Step 5(커밋) 순으로 진행한다. (`superpowers:test-driven-development` 참조)
  - 작업 중 diff가 200줄을 넘어갈 것 같으면 Task를 더 쪼개거나 서브 이슈로 재분리한다.
  - **plan이 크게 변경되거나 다른 문제가 발생하였을때 작업을 멈추고 요청자에게 문제 내용, 방향성, 장단점을 작성하여 검토 받는다.** 방향이 바뀌면 readme.md/api-spec.md/page-spec.md/plan.md 등 상위 문서도 함께 갱신한다.
  - `plan`에 따라 작업시 단계별로 나눈 경우 단계 작업이 끝난후 요청자에게 검증 요청을 한다 검증시 작업 내용을 간략하게 중요한 내용(주요 로직, 사이드 이팩트 위험성이 큰 코드)리스트화 해서 요청자에게 전달한다.
  - "완료"라고 보고하거나 커밋하기 전에 `superpowers:verification-before-completion`에 따라 실제 검증 명령(테스트/빌드 등)을 실행하고 결과를 확인한다.
  - 수정및 개선후 다음 단계 진행을 요청 받을 경우 커밋하고 다음 작업을 진행한다.

### 작업 완료 후

- 브리핑
  - 진행한 작업 간략하게 리스트화
  - 주요 로직 간략한 설명
  - 주요 로직 파일 리스트화
  - 사이드 이팩트, 위험 요소 리스트화

## PR 생성

- PR 만들기 전 `code-review` 스킬로 diff 자체 리뷰를 진행하고, 발견된 이슈를 반영한다.
- .github/PULL_REQUEST_TEMPLATE/feature.md에 내용을 기반으로 pr 작성
- 머지는 수동으로 진행한다. (브랜치 정리 등 자동화는 추후 추가)

### PR 생성 완료 후

- 브리핑
  - PR 링크 전달
