# 디자인 목업 작업 방향 (2차 재작업, 2026-07-28)

## 재작업 배경

- 1차 산출물(Design.pdf, 07-19)의 문제: 디자인 시스템 없이 화면부터 만들어 개성이 없고, AI가 만든 정적인 느낌이 남. 기획 내용도 이후 많이 바뀜
- 이번엔 화면을 만들기 전에 "느낌·참고·움직임 규칙"을 텍스트로 먼저 정해두고, 각 단계마다 통과 조건을 정해서 넘어가기 전에 확인함
- "AI가 만든 정적인 느낌" 문제는 코드로 옮긴 뒤 taste-skill로 따로 해결함
- 와이어프레임(뼈대만)과 목업(색 입히기)을 분리함 — 색상 시스템은 먼저 정해두되, 화면 작업은 "색 없는 뼈대 확인" → "색 입히기" 순서로 진행. 뼈대 문제와 색 문제를 같이 보면 뭐가 잘못됐는지 구분이 안 됨

> 단계는 번호가 아니라 이름으로 참조한다. 중간에 단계를 추가/삭제해도 뒤 단계 번호를 전부 고칠 필요가 없도록 하기 위함.

# 작업 내용

## 기본 자료 조사 및 PRD 준비

어떤 브랜드 가치를 만들지 어떤 문제를 해결할지 정의하여 디자인 방향성에 도움을 주기 위한 문서 준비

### PRD 문서 정리
- 브랜드 정의서, 기능 명세서, 화면 정의서 제작

### 문서 정합성 확인
- 기능 명세서와 화면 정의서 내용이 서로 안 맞는 부분 없는지 확인
- 최근 바뀐 기획(액션포인트 입력 방식 등)이 화면 정의서에 반영됐는지 확인
- 화면 크기·지원 브라우저(데스크톱 1440px, 크롬 전용) 다시 한번 확정

## 디자인 방향 정의 (도구 진입 전)

클로드 디자인에 개성을 넣기 위한 기초 작업 — 이 재료가 없으면 AI가 밋밋한 기본값으로 만듦

### 톤앤매너 키워드 정하기
- 서비스 느낌을 나타내는 형용사 3~5개 선정 (신뢰감 있는 성장 기록 vs 가볍고 재미있는 습관 트래커처럼, 방향에 따라 색 채도·타이포 굵기·여백 밀도가 전부 갈림)
- 통과 기준: 키워드만 보고 제3자가 화면을 그릴 수 있으면 통과, "좋은 느낌" 식으로 추상적이면 재작업

### 참고 서비스 벤치마킹
- 통짜로 "이 서비스처럼"이 아니라 색상은 A, 타이포 밀도는 B, 인터랙션은 C처럼 요소 단위로 발췌
- 디딧
- 리니어
- 대시보드
    - 인프런
    - git
    - 등등

### 인터랙션/모션 원칙 정하기
- 정적으로 보이는 원인은 보통 hover/active/focus/disabled 상태 부재, 전환 효과 부재
- 최소 정의: 버튼 hover/active, 카드 hover, 로딩 스켈레톤 유무, 페이지/모달 전환 방식
- 통과 기준: "느낌"이 아니라 텍스트로 정의돼 있어야 함 (실제 모션 구현의 상당 부분은 코드 반영 단계의 taste-skill에서 다시 채워짐 — 여기선 방향만 명시)

### 비슷한 디자인 시스템 조사
- 토스
- 리니어
- github

**다음 단계로 넘어가는 조건**: 위 네 가지(톤앤매너/벤치마킹/인터랙션 원칙/비슷한 디자인 시스템)가 문서로 준비돼야 다음 단계(디자인 시스템 세팅) 진행

## Claude Design 2.1 디자인 시스템 세팅

색상/폰트/컴포넌트처럼 계속 재사용할 디자인 값들을 클로드 디자인 툴로 확정하는 단계

### 세팅 절차
- claude.ai/design 접속 → 조직 생성/선택
- 기능명세서, 화면정의서, 앞서 만든 톤앤매너·벤치마킹·인터랙션 문서 업로드 (기존엔 색상 hex만 있는 스타일 문서만 올렸던 게 개성 부재의 원인 중 하나 — 이번엔 정성적 방향 문서도 함께 투입)
- 추출된 디자인 시스템(컬러, 타이포, 컴포넌트, 레이아웃, 상태값)이 앞 단계에서 정한 방향과 맞는지 확인
- 안 맞으면 Remix로 수정 요청, 맞으면 Published로 전환

### 검토 방법
- 색상/폰트/상태값을 실제 값으로 뽑아서 대조 (체크리스트: `checklist-design-system-review.md`)
- 여기서 어긋나면 이후 모든 화면에 그대로 퍼지므로, 통과한 뒤에만 다음 단계로 진행

### 주의할 점
- 이 단계는 "색상 시스템 자체"만 만드는 것 — 아직 어떤 화면에도 적용한 게 아님
- 화면에 색을 입히는 건 다음다음 단계(디자인 목업)부터. 여기서 화면까지 같이 요청하면 와이어프레임과 목업이 뒤섞임

## 앵커 화면 와이어프레임 (그레이스케일, 구조만)

색이나 폰트 없이 뼈대(레이아웃, 구성요소, 상태)만 먼저 확인하는 단계

### 작업 방법
- 화면은 **S-03 대시보드**로 먼저 진행 — 히트맵/배지/리스트/CTA 등 구성요소 밀도가 가장 높아서, 여기서 뼈대가 안 깨지면 나머지 화면은 대부분 하위집합으로 커버됨
- 클로드 디자인에 "색상·타이포 적용 없이 회색조로, 레이아웃과 구성요소 배치만" 명시적으로 요청
- `04-screen-spec.md` S-03 항목을 빠짐없이 반영 요청 (Empty/Loading/Error 상태 포함)

### 통과 조건
- 화면정의서 구성요소·상태 누락 없음
- 중요한 정보가 크게, 덜 중요한 정보가 작게 배치됐는지 (화면정의서 우선순위와 일치)
- 버튼·토글·입력 등 눌러야 하는 요소가 구조상 다 보이는지 (색은 아직 없어도 됨)

### 막히면
- 뼈대 자체가 3번 이상 계속 흔들리면 색 문제가 아니라 `04-screen-spec.md` 자체가 불완전하다는 신호 — 화면정의서부터 재점검

## 디자인 목업 (와이어프레임에 디자인 시스템 적용)

통과된 뼈대 위에 디자인 시스템의 색·폰트·인터랙션을 입히는 단계

### 작업 방법
- 클로드 디자인에 "이 와이어프레임의 레이아웃·구성요소 배치는 그대로 유지하고, 디자인 시스템의 색상·타이포만 적용해줘"라고 명시적으로 요청 (레이아웃 재배치 금지)

### 통과 조건
- 와이어프레임 구조가 그대로 유지됨 (색만 추가됐고 레이아웃이 바뀌지 않음)
- 톤앤매너 키워드와 부합 (제3자 리뷰 권장)
- 인터랙션 원칙 최소 1개 이상 화면에서 확인 가능
- 디자인 시스템 토큰과 색상/타이포 100% 일치

### 막히면
- 스타일 수정은 3회까지만 반복. 그 이상 흔들리면 디자인 방향 정의 단계(톤앤매너)로 되돌아갈 것 — 스타일이 안 잡히는 건 방향 정의가 약하다는 신호

## 스타일 확정 후 순차 확장

앵커 화면이 통과된 이후, 같은 방식으로 나머지 화면 확장

### 작업 방법
- 앵커 화면이 목업 단계 통과 조건을 만족한 뒤에만 진행 (통과 전 다음 화면 동시 생성 금지 — 톤 드리프트 재발 방지, 과거 실패 패턴)
- 각 화면도 동일하게 "와이어프레임 → 목업" 순서를 따르되, 이미 검증된 구조 패턴(리스트, 카드, 모달 등)은 재검증 없이 재사용 가능
- 5개 이하 배치로 진행: S-01, S-04, S-05 먼저 → S-06~S-09
- 화면마다 생성 직후 화면정의서 대조 + 앵커 화면과 색상 hex/폰트/radius 대조

## 코드 반영 + taste-skill 적용

화면이 다 확정되면 실제 코드로 옮기고, AI가 만든 밋밋한 느낌을 마무리로 다듬는 단계

### 코드 반영
- 화면 확정 후 `/design-sync`(Claude Code)로 Next.js + Tailwind + shadcn 코드 스캐폴딩

### taste-skill 적용
- 설치: `npx skills add https://github.com/Leonxlnx/taste-skill --skill "design-taste-frontend"`
- `MOTION_INTENSITY`, `DESIGN_VARIANCE`, `VISUAL_DENSITY` 3개 dial을 앞서 정한 톤앤매너/인터랙션 원칙에 맞게 조정
- 스캐폴딩 직후 첫 적용은 기본값(`design-taste-frontend`), 이후 반복 개선이 필요하면 `redesign-existing-projects`(기존 코드 감사 후 레이아웃/여백/위계 보정 전용 변형) 사용

### 다듬은 뒤 확인
- 적용 전/후 스크린샷을 나란히 놓고 "AI가 만든 정적인 느낌"이 실제로 줄었는지 확인
- **taste-skill 결과 평가 후에만** v0/Stitch 재도입 여부 결정 (처음부터 병행하지 않음) — 부족하면 taste-skill의 `stitch-design-taste` 변형이 Stitch용 `DESIGN.md` 포맷을 지원하므로 그대로 연결 가능

## 참고: taste-skill은 코드 단계에서만 쓰는 도구

- Claude Design 안에서는 못 쓰고, 실제 프론트엔드 코드(React/Vue/Svelte)에만 적용되는 스킬
- 그래서 "AI가 만든 정적인 느낌" 문제는 와이어프레임·목업 단계가 아니라 코드 반영 단계(스캐폴딩 이후)에서 실질적으로 해결됨
- 목업 단계에서 인터랙션 원칙을 "확인 가능"한 수준까지만 요구하는 이유이기도 함 (완성은 코드 반영 단계 몫)

## 도구별 역할 분담

- **Claude Design**: 화면 구조(와이어프레임), 색상·타이포 적용(목업), 구성요소·상태 누락 검증, 디자인 시스템(토큰) 일관성 관리
- **taste-skill**: 코드 단계에서 레이아웃 변주·모션·밀도 보정 (anti-slop)
- **v0 / Stitch**: taste-skill 적용 후에도 부족할 때만 재도입하는 보조 비주얼 완성 도구
